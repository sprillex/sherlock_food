The database generated by the script is a single, compact SQLite table called restaurants. It is built to serve as an indexed, offline data cache for your Android app.

Here is a breakdown of every column, how the data is mapped from OpenStreetMap (OSM), and how you will use each piece in Android.
Column Breakdown
Column Name	SQLite Type	Origin in OpenStreetMap	Description & App Usage
id	INTEGER	el["id"]	Primary Key. The stable 64-bit OSM element identifier. Because this is unique in OSM, your app can re-fetch updates and perform SQLite UPSERT operations without creating duplicate rows or messing up existing relations.
name	TEXT	tags["name"]	The public, display name of the venue (e.g., "Tony Packo's Cafe", "Balance Pan-Asian Grille"). Rows missing this tag are filtered out during ingestion so your UI never shows blank tiles.
amenity	TEXT	tags["amenity"]	The broad business classification. OpenStreetMap standardizes food and drink venues into primary categories: restaurant (sit-down/table service), fast_food (counter service/drive-thru), cafe (coffee/light bites), bar, and pub. Ideal for high-level UI category filters/chips.
cuisine	TEXT	tags["cuisine"]	The culinary focus (e.g., mexican, pizza, chinese, burger;american). OSM often separates multiple cuisines with semicolons. Can be NULL if not specified by an OSM contributor.
street	TEXT	tags["addr:street"]	Street name (e.g., "Front Street", "Monroe Street"). Can be NULL.
housenumber	TEXT	tags["addr:housenumber"]	Building or suite number (e.g., "1902", "5800"). Stored as TEXT rather than an integer because addresses can have letters, hyphens, or suite tags (e.g., "102B", "45-A").
postcode	TEXT	tags["addr:postcode"]	ZIP code (e.g., "43605", "48161"). Stored as TEXT to preserve leading zeroes or alphanumeric codes.
city	TEXT	tags["addr:city"]	The municipality (e.g., "Toledo", "Sylvania", "Perrysburg", "Monroe", "Adrian"). Allows quick grouping or filtering by town.
phone	TEXT	tags["phone"] or tags["contact:phone"]	Business phone number. Useful in Android to trigger an intent: Intent(Intent.ACTION_DIAL, Uri.parse("tel:$phone")).

longitude	REAL	el["lon"] or el["center"]["lon"]	64-bit IEEE floating-point longitude coordinate.

Understanding the Coordinate Resolution

In OpenStreetMap, real-world objects are modeled as either nodes (points) or ways/relations (building polygons, strip-mall outlines):

    A standalone coffee cart or small suite is typically a node, where lat and lon are directly attached.

    A standalone restaurant building is typically a way, which is a series of perimeter points forming a polygon.

    The query uses out center tags;, which tells the Overpass server to compute the geographic centroid (geometric center) of any polygon. The Python script maps both cases cleanly into flat latitude and longitude fields so your Android app doesn't have to deal with complex polygon geometry.

What the Indices Do

The script explicitly builds four B-tree indices in SQLite:

    index_restaurants_latitude_longitude on (latitude, longitude):

        Why it matters: Without this, every time the user pans or zooms a map, SQLite would perform a full table scan across all ~3,500 rows to find what fits on screen. With this index, bounding-box queries (WHERE latitude BETWEEN ? AND ? AND longitude BETWEEN ? AND ?) resolve in single-digit milliseconds.

    index_restaurants_amenity:

        Speeds up toggle filters (e.g., showing only cafe or only restaurant).

    index_restaurants_cuisine:

        Speeds up keyword searches on cuisines (e.g., WHERE cuisine LIKE '%pizza%').

    index_restaurants_city:

        Allows fast grouping or filtering by specific towns across the four counties.

What "Offline-First" Means for This Database in Android

    Zero Initial Network Dependency: Because this .db file is compiled ahead of time and bundled into app/src/main/assets/, Room unpacks it on the first launch. A user in a dead zone can immediately launch the app, see every restaurant across Lucas, Wood, Monroe, and Lenawee counties, run searches, and view locations.

    Separation of Concerns: Because the table strictly uses OSM's immutable id as its @PrimaryKey, you can create a second user table (e.g., user_favorites or visited_logs) referencing restaurant_id as a foreign key. When you eventually pull fresh Overpass data over the air, you can run @Upsert on the restaurants table without wiping or modifying the user's personal app data.
